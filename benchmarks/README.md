# Benchmarks

Every table below is generated by a script from a run's machine-readable output. Do not
retype numbers: rerun the script and paste the Markdown it prints.

```sh
cargo build --release
ORCHESTRATE=target/release/orchestrate python3 benchmarks/landline_latency/run.py
```

The script writes CSV, JSON, and Markdown under `benchmarks/results/` (gitignored), and
the JSON carries an environment header: CPU, OS, architecture, `orchestrate`, `rustc`,
`cargo`, Python, the TypeScript toolchain and backend, the wasmtime version, the sample
counts, the commit SHA, and whether the tree was dirty. Python 3.10+ is required.

The benchmark does not run in CI, because shared runners are too noisy for timing. CI only
checks that `landline_latency/main.orch` still typechecks.

## landline_latency — the boundary ladder

Measures round-trip call latency — from calling a serverlet handler until its reply
arrives — for the same echo handlers on every serverlet boundary, and the cost of the
two rungs below a serverlet call:

| Kind | Where the handler runs |
|---|---|
| `local-let` | Not a call: a plain `let` incremented in a loop (the compiler folds it; the row shows the floor of this method) |
| `shared-let` | Not a call: a `shared let` incremented in a loop — one mutex, taken once per statement |
| `in-process` | An ordinary serverlet: a channel hop inside the program (the baseline) |
| `sandbox` | A sandboxed serverlet: a wasmtime guest, called through the same actor loop |
| `secret` | A Rust child process, over stdin/stdout |
| `python` | A Python landline, over stdin/stdout |
| `typescript` | A TypeScript landline: a compiled executable over stdin/stdout |

Four sweeps, each with warm-up calls first and the tail reported:

- **Payload sweep.** An `int`, a 1,024-character `string`, and a 1,000-element `int[]`,
  called back to back: 200 warm-up calls, then 2,000 measured, one caller.
- **Call-rate sweep.** The `int` payload paced at 100 Hz and 1 kHz, where the caller
  sleeps between calls so the child and the actor really go idle, as they would under a
  host that ticks, and at 10 kHz, where the caller spins, because `sleep` has millisecond
  resolution. Fewer samples at the slow rates keep the run short.
- **Concurrent callers.** The `int` payload with 2, 4, and 8 callers sharing one
  serverlet, each a branch of a `parallel` block making 200 warm-up and 1,000 measured
  calls; every sample is one caller's round trip, so the rows show what queueing behind
  other callers costs. The 1-caller row is the payload sweep's `int` row.
- **State rungs.** `clock_micros` has microsecond resolution, so each sample is a batch
  of 1,000 statements: the elapsed microseconds of a batch are nanoseconds per
  statement. `loop-only` is the counting loop by itself.

The TypeScript rung needs Bun and TypeScript 7 (see the [TypeScript SDK](../sdk/typescript/README.md));
without them `run.py` strips that rung and says so in the header. Run with `--no-typescript`
to skip it on purpose. The program prints one `kind,payload,rate,micros` line per sample
and `run.py` computes p50, p90, p99, and max.

Reading the results:

- Numbers depend on the machine, OS scheduler, and load. Compare cases on one machine.
- For per-tick work, the tail (p99, max) matters more than the median. Use it to choose a
  landline `budget`.
- The paced rows are the ones a ticking host should read: a caller that idles pays the
  wake-up of the actor or the child on every call.
- Under concurrent callers, an in-process or sandboxed serverlet keeps its per-call
  latency, because the actor turns calls over faster than callers queue them; a child
  process does not, and the queue shows in every caller's round trip.
