# Benchmarks

Every table below is generated by a script from a run's machine-readable output. Do not
retype numbers: rerun the script and paste the Markdown it prints.

## One command

```sh
python3 benchmarks/run_all.py
```

builds `target/release/orchestrate` and runs the three scripts below in order, writing
every table under `benchmarks/results/` (gitignored) and joining the three Markdown
reports into `results.md`. `--no-typescript` skips the TypeScript rung of the ladder,
`--skip <name>` leaves a step out, `--out DIR` writes elsewhere, and `ORCHESTRATE=<path>`
uses a compiler you already built. Run it on an idle machine: two of the three are timing
benchmarks. Python 3.10+ is required.

| Script | Table | Output |
|---|---|---|
| `benchmarks/landline_latency/run.py` | the boundary ladder: payload, call-rate, concurrent-callers, and state sweeps | `boundary_ladder.{csv,json,md}`, `boundary_ladder_samples.csv` |
| `benchmarks/tick_cost/run.py` | the library-mode tick cost | `tick_cost.{csv,json,md}` |
| `benchmarks/diagnostics_coverage.py` | how many invalid programs `orchestrate check` rejects | `diagnostics_coverage.{csv,json,md}` |

Each script can also run alone:

```sh
cargo build --release
ORCHESTRATE=target/release/orchestrate python3 benchmarks/landline_latency/run.py
ORCHESTRATE=target/release/orchestrate python3 benchmarks/tick_cost/run.py
ORCHESTRATE=target/release/orchestrate python3 benchmarks/diagnostics_coverage.py
```

Each writes CSV, JSON, and Markdown under `benchmarks/results/`, and the JSON carries an
environment header: CPU, OS, architecture, `orchestrate`, `rustc`, `cargo`, Python, the
TypeScript toolchain and backend, the wasmtime version, the sample counts, the commit
SHA, and whether the tree was dirty.

Neither benchmark runs in CI, because shared runners are too noisy for timing. CI only
checks that `landline_latency/main.orch` still typechecks.

## landline_latency — the boundary ladder

Measures round-trip call latency — from calling a serverlet handler until its reply
arrives — for the same echo handlers on every serverlet boundary, and the cost of the
two rungs below a serverlet call:

| Kind | Where the handler runs |
|---|---|
| `local-let` | Not a call: a plain `let` incremented in a loop (the compiler folds it; the row shows the floor of this method) |
| `shared-let` | Not a call: a `shared let` incremented in a loop — one mutex, taken once per statement |
| `in-process` | An ordinary serverlet: a channel hop inside the program (the baseline) |
| `sandbox` | A sandboxed serverlet: a wasmtime guest, called through the same actor loop |
| `secret` | A Rust child process, over stdin/stdout |
| `python` | A Python landline, over stdin/stdout |
| `typescript` | A TypeScript landline: a compiled executable over stdin/stdout |

Four sweeps, each with warm-up calls first and the tail reported:

- **Payload sweep.** An `int`, a 1,024-character `string`, and a 1,000-element `int[]`,
  called back to back: 200 warm-up calls, then 2,000 measured, one caller.
- **Call-rate sweep.** The `int` payload paced at 100 Hz and 1 kHz, where the caller
  sleeps between calls so the child and the actor really go idle, as they would under a
  host that ticks, and at 10 kHz, where the caller spins, because `sleep` has millisecond
  resolution. Fewer samples at the slow rates keep the run short.
- **Concurrent callers.** The `int` payload with 2, 4, and 8 callers sharing one
  serverlet, each a branch of a `parallel` block making 200 warm-up and 1,000 measured
  calls; every sample is one caller's round trip, so the rows show what queueing behind
  other callers costs. The 1-caller row is the payload sweep's `int` row.
- **State rungs.** `clock_micros` has microsecond resolution, so each sample is a batch
  of 1,000 statements: the elapsed microseconds of a batch are nanoseconds per
  statement. `loop-only` is the counting loop by itself.

The TypeScript rung needs Bun and TypeScript 7 (see the [TypeScript SDK](../sdk/typescript/README.md));
without them `run.py` strips that rung and says so in the header. Run with `--no-typescript`
to skip it on purpose. The program prints one `kind,payload,rate,micros` line per sample
and `run.py` computes p50, p90, p99, and max.

Reading the results:

- Numbers depend on the machine, OS scheduler, and load. Compare cases on one machine.
- For per-tick work, the tail (p99, max) matters more than the median. Use it to choose a
  landline `budget`.
- The paced rows are the ones a ticking host should read: a caller that idles pays the
  wake-up of the actor or the child on every call.
- Under concurrent callers, an in-process or sandboxed serverlet keeps its per-call
  latency, because the actor turns calls over faster than callers queue them; a child
  process does not, and the queue shows in every caller's round trip.

## tick_cost — library mode

Measures the glue around a synchronous library tick: `tick_sync` on a current-thread
runtime, with an empty body, one host call, five host calls, an instance `let`
increment, a `shared let` increment, and one host-fired event per tick, next to the
`Host` trait method called through its vtable alone, which is the floor for a host call.
Each case is its own program built with `build --lib` and driven by one Rust host in
release mode: five warm-up rounds, then 21 rounds of 200,000 ticks; the number reported
is the median round, with the fastest and the p90 round beside it. The fastest round is
the figure to quote: the OS moves the thread between core types and clock states during
a run, so medians overlap between cases within a few nanoseconds.

### Sample results


One run on Apple M2 (macOS-15.3.2-arm64-arm-64bit, arm64), 2026-09-21T03:55:18+00:00, commit `afbc07fb4be4`. rustc 1.98.1 (48a229cea 2026-09-01). Nanoseconds per `tick_sync` on a current-thread runtime: the median of 21 rounds of 200,000 ticks, after 5 warm-up rounds. Your numbers will differ.

| Case | ns per tick (median) | fastest round | p90 round |
|---|---:|---:|---:|
| host_method_alone | 1.97 | 1.96 | 1.99 |
| empty | 6.16 | 6.06 | 6.35 |
| one_call | 7.27 | 7.08 | 7.43 |
| five_calls | 14.28 | 12.59 | 14.46 |
| instance_let | 6.28 | 6.24 | 6.39 |
| shared_let | 11.68 | 10.86 | 11.93 |
| event | 211.34 | 196.99 | 226.94 |

Derived from the fastest rounds, which move least between runs: an empty tick costs 6.06 ns; each host call in a tick costs 1.38 ns (five calls minus one, over four), against 1.96 ns for the trait method called through its vtable alone. The empty tick and the one-call tick are within noise of each other at this resolution.

Medians overlap between cases within a few nanoseconds: the OS moves the thread between core types and clock states during a run, which is why the fastest round is reported beside them. Run on an idle machine, and compare cases within one run.

## diagnostics_coverage — what `orchestrate check` rejects

Runs every program in `tests/error_cases/diagnostics/`, each deliberately invalid,
through `orchestrate check` and then `orchestrate build`, and classifies where it was
rejected: by `check`, by the build before Cargo runs, through Cargo without a rustc error
code, by rustc against generated code (a leak, held to `KNOWN_LEAKS.txt` by the test
`diagnostics_never_leak_rustc`), or not at all. The same classification is asserted by
`cargo test`; the script writes it as a table with the counts the paper states.

### Sample results


84 deliberately invalid programs in `tests/error_cases/diagnostics/`, run on 2026-09-21T03:55:25+00:00 at commit `afbc07fb4be4` with OrchestrateLang compiler v0.14.0.

| Rejected by | Programs | Meaning |
|---|---:|---|
| `orchestrate check` | 76 | the typechecker's own error, before any code is generated |
| build, before Cargo | 6 | codegen or the driver, still the compiler's own error |
| Cargo, no rustc code | 0 | a `compile_error!` the generator planted, reported through Cargo |
| rustc | 2 | leaked: a rustc error against generated code |
| nothing | 0 | wrongly accepted |

**76 of 84 invalid programs are rejected by `orchestrate check`.**
82 of 84 are rejected as the compiler's own error before Cargo runs; 0 more are rejected through Cargo without a rustc error code; 2 leak a rustc error; 0 are wrongly accepted.

The per-case rows are in `benchmarks/results/diagnostics_coverage.md` after a run.
