When to use what

Where OrchestrateLang fits, and where it does not.

Four well-known ways to coordinate concurrent work, compared with OrchestrateLang on the axes that decide a choice: what it compiles to, what owns state, what happens on failure, how other languages plug in, and whether it crosses machines. No scores. Several of these are the right answer for problems OrchestrateLang is not built for, and the page says so.

Choose

Reach for each one when.

OrchestrateLang when

The coordination shape should be readable, native, and polyglot.

  • You want workers, reactions, services, and the lifecycle owner to be visible in the source rather than assembled from library calls.
  • The program must be a native binary, or a crate a Rust host embeds and ticks.
  • Existing C, C++, Zig, Swift, Rust, TypeScript, or Python code should plug in at the cheapest boundary that works.
  • One process is the scope. Distribution and durability are not requirements.
Not yet for: untrusted code (sandboxing is not shipped), multi-machine systems, or anything that needs supervision trees more elaborate than per-worker restart policies.
Tokio by hand when

You need every knob and no second language.

  • The team is fluent in async Rust and the coordination logic is small or unusual.
  • You need runtime features OrchestrateLang does not expose: custom executors, io_uring, precise scheduling.
  • Adding a compile step and a language to the build is not worth it for the size of the coordination layer.
Cost: the topology lives in the implementation, and supervision is yours to write and keep correct. OrchestrateLang generates this code; ORCH_SHOW_GENERATED=1 shows exactly what you would otherwise write.
Erlang / OTP when

Fault tolerance and distribution are the product.

  • Supervision trees, hot code loading, and distributed processes are first-order requirements.
  • The BEAM's scheduling and isolation guarantees matter more than native performance.
  • Elixir or Erlang is an acceptable implementation language for the whole system.
Trade: a VM, and calling native code means NIFs or ports rather than a direct call. OrchestrateLang borrows the actor-with-private-state idea and compiles it to Rust instead.
Akka when

You are on the JVM and want actors with clustering.

  • The application is Scala or Java and the actor model fits the domain.
  • You need cluster sharding, persistence, or streams from one toolkit.
Trade: the JVM, and non-JVM code goes over a network boundary. Check the current license terms for your use before adopting.
Temporal when

Work must survive crashes, deploys, and weeks of waiting.

  • Business processes span minutes to months and must never be lost.
  • Retries, timers, and human-in-the-loop steps need to be durable and observable.
  • Running or renting a server cluster is acceptable.
Trade: an external service and a replay-based programming model. OrchestrateLang coordinates work inside one process at microsecond cost; Temporal coordinates work across a fleet at durable-execution cost. They solve different problems and can coexist: a Temporal activity could be an OrchestrateLang binary.
The same worker, twice

What the language removes.

A supervised polling worker with an event handler. Left: the OrchestrateLang source. Right: the shape of the Rust a careful engineer writes by hand for the same behavior, abbreviated. The generated code for every example is on the examples page under "Generated Rust".

worker.orch
let poller = automatic(restart: 3) {
    let reading = read_sensor()
    if reading > 90 {
        trigger overheated(reading)
    }
    sleep(500)
} on_crash error {
    print("poller crashed: {error}")
}

let alarm = on overheated(reading: int) {
    print("temperature is {reading}")
}

orchestrator main(workers: process[poller]) {
    on_stop { print("bye") }
}
by hand, sketch
// an event bus for `overheated`
let (tx, mut rx) = broadcast::channel::<i64>(64);

// the handler
let alarm = tokio::spawn(async move {
    while let Ok(reading) = rx.recv().await {
        println!("temperature is {reading}");
    }
});

// the supervised worker
let poller = tokio::spawn(async move {
    let mut attempts = 0;
    loop {
        let result = AssertUnwindSafe(async {
            loop {
                let reading = read_sensor();
                if reading > 90 { let _ = tx.send(reading); }
                sleep(Duration::from_millis(500)).await;
            }
        }).catch_unwind().await;
        if let Err(e) = result {
            eprintln!("poller crashed: {e:?}");
            attempts += 1;
            if attempts > 3 { break; }
        }
    }
});

// lifecycle: Ctrl+C, abort handles, join, on_stop …
tokio::signal::ctrl_c().await?;
poller.abort(); alarm.abort();
println!("bye");
A note on fairness. This page is written by the OrchestrateLang project, so read the "choose" column with that in mind. The comparison deliberately excludes scores: the systems above are older, larger, and better tested than a v0.8 language, and several of them solve problems OrchestrateLang does not attempt. If a row misstates another project, open an issue and it will be corrected.
