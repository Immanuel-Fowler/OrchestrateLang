# OrchestrateLang: work needed for Ackee Game Engine

This is a task list for the **OrchestrateLang** repo (github.com/Immanuel-Fowler/OrchestrateLang). Every task comes from a requirement in **Ackee Game Engine** (a Rust game engine). Ackee Game Engine will link a crate generated by `orchestrate build --lib` and drive it from its frame loop.

You may not have the Ackee Game Engine repo open, so each task states the engine fact it depends on. `AGE:` paths point into the Ackee Game Engine repo. All other paths are in OrchestrateLang.

**Status key:**
- **Planned**: already on a to-do in OrchestrateLang's docs (location given).
- **Known limitation**: written down, not scheduled.
- **Not in docs**: new work.

Follow `CONTRIBUTING.md` for names, commits and releases. Add tests next to the existing library tests in `tests/library_tests.rs`, and update `docs/library-mode.md` and `CHANGELOG.md` for every user-visible change.

---

## How Ackee Game Engine will use the library (facts to design against)

- **The frame loop is synchronous and single-threaded.** Systems are `FnMut(&mut World)` (`AGE: crates/ackee_engine/src/schedule.rs:68`). The engine has no async runtime and no tokio.
- **The `World` is not `Send`** (`AGE: docs/ARCHITECTURE.md:59`). A `Host` implementation (`Send + Sync + 'static`, `&self`) can't reach the world directly. It can only queue requests or read data handed to it.
- **There are two update rates.** `FixedUpdate` runs at 60 Hz, at most 8 steps a frame, before physics. `Update` runs once per frame (`AGE: docs/ARCHITECTURE.md:122`). Native scripts get `on_tick(dt)` and `on_fixed_tick(step)` (`AGE: docs/ARCHITECTURE.md:71`).
- **Replays must be deterministic.** The same recorded input must produce the same report, compared byte for byte in CI (`AGE: docs/ARCHITECTURE.md:178`, `AGE: docs/ROADMAP.md:120`).
- **Rust crates must use edition 2024 and `rust-version` >= 1.89.** CI enforces this on every workspace package (`AGE: docs/ROADMAP.md:121`, `AGE: scripts/check-rust-editions.sh`, `AGE: .github/workflows/ci.yml:179-192`).
- **Shipped games are statically linked.** `ackee package --static` generates a player crate with its own empty `[workspace]` table (`AGE: crates/ackee_cli/src/static_player.rs:110-111`). Statically linked code never hot reloads (`AGE: docs/ARCHITECTURE.md:74`).
- **The editor has play-in-editor.** Play spawns a copy of the scene, and Stop discards it (`AGE: docs/ARCHITECTURE.md:183`). Expect `start` and `shutdown` once per play session.
- **Logging goes through `tracing`** (`AGE: docs/ARCHITECTURE.md:28`).
- **Engine values** (`AGE: crates/ackee_reflect/src/lib.rs:397-419`) include `f32` vectors, quaternions and colors, `Entity(u64)` (generation in the high 32 bits, index in the low 32), strings, arrays and structs.
- **Web is planned for later** (Ackee Game Engine Phase 11; the current phase is 8). Runtime crates must pass `cargo check --target wasm32-unknown-unknown` (`AGE: docs/ROADMAP.md:119`). The web player is single-threaded with no SharedArrayBuffer (`AGE: docs/ROADMAP.md:602`), and web scripting is static linking only (`AGE: docs/ROADMAP.md:610`).

## Priority 1: needed before the engine can link the crate at all

### ✅ 1. Let generated crates build inside another Cargo workspace
- **Why:** game projects live inside the Ackee Game Engine repo, whose root `Cargo.toml` has a `[workspace]`. `run_build_library` runs `cargo check` in `.orch_cache/library` next to the input file. Cargo walks up to the engine's workspace and fails with "current package believes it's in a workspace when it's not". The generated secret-serverlet `cargo build --bins` has the same problem.
- **Where:** `src/driver.rs`, in the Cargo.toml template (around line 380) and `run_build_library` (line 642).
- **Do:** emit an empty `[workspace]` table in the cache crate's `Cargo.toml`, as `AGE: crates/ackee_cli/src/static_player.rs:110-111` does. Decide whether the output crate at `-o <dir>` also gets one. It must still work as a path dependency of another crate.
- **Status:** Not in docs.
- **✅ Verified:** `engine_workspace_and_latest_rust_metadata` builds an `.orch` library and secret child beneath an unrelated Cargo workspace. Cache crates have their own empty workspace; output crates omit it so they can join the host workspace as normal path dependencies.

### ✅ 2. Generate crates using the latest stable Rust compiler and edition
- **Why:** the Ackee Game Engine edition guard rejects any workspace package below edition 2024 or without `rust-version >= 1.89`. A game module that depends on the generated crate by path makes it a workspace member.
- **Where:**
  - `src/driver.rs:382` hard-codes `edition = "2021"`.
  - `src/ffi_parser.rs:11` emits `extern "C" {`, which edition 2024 rejects (it needs `unsafe extern "C"`).
  - `src/codegen/stmt.rs:717` emits `#[no_mangle]` (sandbox guest only; edition 2024 needs `#[unsafe(no_mangle)]`).
  - Also check generated code for identifiers named `gen` (reserved in 2024; escape as `r#gen`) and for the 2024 `if let` / tail-expression temporary drop changes around `Mutex` locks (e.g. `src/codegen/stmt.rs:341`).
- **Do (user override, 2026-09-15):** use the latest stable compiler, Rust **1.98.1**, with `rust-version = "1.98.1"`. Edition **2024** is still the newest stable edition, so generated libraries use `edition = "2024"`. Installed and verified: `rustc 1.98.1 (48a229cea 2026-09-01)`. Verified by workspace/metadata, C/C++ library, reserved-identifier, and snapshot tests.
- **Status:** Not in docs.
- **Done when:** the snapshot and runtime tests pass for a 2024 library build, including `load_foreign "c"` / `"cpp"` modules. A generated crate passes a copy of the Ackee Game Engine guard: `cargo metadata --no-deps` shows edition >= 2024 and rust-version >= 1.89.

### ✅ 3. Synchronous driving from a host with no async runtime
- **Why:** engine systems are plain `FnMut(&mut World)`. The engine will own a current-thread tokio runtime only for the library and call it from a system. With a current-thread runtime, landline readers, `automatic` blocks and event handlers only make progress while the host is inside `block_on`.
- **Where:** `src/codegen/library_runtime.rs.txt:93-122` (`ready`, `tick`, `stop_requested`, `shutdown`, `start`), and `docs/library-mode.md:30` and `:54`, which say current-thread works and mention `block_on` but don't define this pumped mode.
- **Do:**
  - Specify and test the "host pumps the runtime only during `tick`" model: what runs between ticks, and what doesn't.
  - Consider blocking wrappers (`tick_blocking(&Runtime, dt)`, etc.) so hosts don't write `block_on` everywhere.
- **Status:** Partly in docs (`docs/library-mode.md:30`, `:54`); pumped mode isn't specified.
- **Done when:** a test drives a library with a current-thread runtime only inside `tick`. Top-level state, `on_tick` hooks, event handlers and a Python landline call all complete within the ticks, and nothing runs between them.
- **✅ Verified:** `engine_current_thread_pumps_workers_events_and_python` pumps a current-thread runtime only through `tick_blocking`. The `on_tick` hook, an event handler, an `automatic` worker, and a Python landline call all complete within the ticks, and the host log doesn't change between them. Documented in `docs/library-mode.md`, "Driving from synchronous code".

### ✅ 4. Host-to-script events (trigger `on` blocks from Rust)
- **Why:** the engine produces events every step: physics contacts, triggers, broken joints and gameplay events. OrchestrateLang's `on name(...)` blocks are the natural receivers, but the generated API has no way for the host to fire an event.
- **Where:**
  - `src/codegen/library.rs`: `library_runtime()` already generates per-instance `event_<name>` registries on `OrchContext`.
  - `src/codegen/library_runtime.rs.txt`: the `Scripts` impl.
- **Do:** generate typed methods on `Scripts`, e.g. `pub fn trigger_<event>(&self, payload...)`, that send into that instance's registry. Define whether handlers run before the next `tick` returns (see task 6).
- **Status:** Not in docs.
- **Done when:** a library test fires `trigger_hit(3)` from Rust and an `on hit(n: int)` block observes it during the next tick, for the right instance only.
- **✅ Verified:** `engine_pumped_events_and_deterministic_replays` fires `trigger_hit(3)` and `trigger_hit(4)` from Rust; each handler runs during the next tick, and a second instance ticked alongside it records nothing from those events. Events queue per instance and run in order before and after each tick. Documented in `docs/library-mode.md`, "Events from the host".

### ✅ 5. Tick input and output batching
- **Why:** `Host` can't read the `World` (it's not `Send`), and host calls return immediately. Queries like "where is the player" need data passed in each tick, and commands like spawn or play sound need to come back out in a batch the engine applies on its own thread.
- **Where:** `src/codegen/library_runtime.rs.txt:101` (`tick(dt)` takes only `dt` and returns `()`), and the design sketch `scripts.tick(dt, input)` at `docs/design/landline-serverlets.md:248`.
- **Status:** **Planned**, build step 8 (`docs/design/landline-serverlets.md:350`). Also `docs/roadmap.md:140`, `docs/library-mode.md:124`, `CHANGELOG.md:43`. The `TICK` frame kind is reserved at `docs/design/landline-serverlets.md:292` and `:310`.
- **Done when:** the `on_tick` declaration can take a typed input struct and produce a typed output, the generated `tick` signature carries both, and a Python landline receives one batched `TICK` frame per tick.
- **✅ Verified:** `engine_typed_tick_and_fixed_step` declares `on_tick(dt: float, input: Input) -> Output`; `tick_blocking(&runtime, dt, input)` returns the `Output`. The Python handler named `tick` receives one TICK frame (kind 9) per call with the tick number and `dt`, and the batch travels inside the input struct's arrays. Documented in `docs/library-mode.md`, "Typed ticks", and the protocol section of `docs/design/landline-serverlets.md`.

## Priority 2: needed for gameplay to behave correctly

### ✅ 6. Deterministic library mode
- **Why:** engine replays must reproduce byte-identical reports. The generated code currently depends on wall-clock time and task scheduling:
  - `sleep` becomes `tokio::time::sleep` (`src/codegen/expr.rs:108`, `:126`, `:152`), and supervision back-off also sleeps (`src/codegen/expr.rs:224`).
  - Each triggered handler runs in its own spawned task, and a full channel drops the event with a warning (`src/codegen/stmt.rs:341`).
- **Do:** add an opt-in deterministic library mode:
  - Time comes from the host's accumulated `dt` (so `sleep` counts ticks, not wall time).
  - Events queued before or during a tick are handled in a defined order before `tick` returns.
  - Events are never silently dropped.
  - Document which features are outside determinism (e.g. landlines).
- **Status:** Not in docs.
- **Done when:** a test runs the same `.orch` library twice with the same sequence of `tick(dt)` values and `trigger_*` calls and records identical host-call sequences, including on a multithreaded runtime.
- **✅ Verified:** `engine_pumped_events_and_deterministic_replays` runs the same library three times (twice on a current-thread runtime, once multithreaded) with the same `tick` and `trigger_*` sequence, including a `sleep` inside an event handler, and gets the identical host-call sequence `[3, 0, 103, 4, 0, 104, 0]`. Excluded from determinism, and rejected at runtime: spawned workers, serverlets and landlines, and `sleep` outside event handlers. Documented in `docs/library-mode.md`, "Deterministic mode".

### ✅ 7. Per-call budgets and late results
- **Why:** a frame at 60 Hz has about 16.6 ms. A slow Python landline inside `tick` must not stall the frame.
- **Where:** design at `docs/design/landline-serverlets.md:202-207` (`budget:`, `late:`), with the limitation noted at `docs/library-mode.md:57`.
- **Status:** **Planned**, build step 8 (`docs/design/landline-serverlets.md:350`).
- **Done when:** a landline that sleeps past its budget doesn't delay `tick`. Its result is applied on the next tick or dropped, as declared.
- **✅ Verified:** build step 8 added `budget` and `late: "drop" | "latest"` landline options (`python_budgets_and_late_results` covers both policies and skipped calls). `engine_host_logs_and_fast_shutdown` calls a Python handler that sleeps 10 seconds under a 20 ms budget, and `tick_blocking` returns in under 100 ms.

### ✅ 8. A fixed-step hook to match the engine's two update rates
- **Why:** gameplay that affects physics runs in the engine's fixed 60 Hz step (`on_fixed_tick`), separate from the per-frame `on_tick`.
- **Where:** `src/codegen/library.rs` `library_entry()` (handles `OnStart`, `OnStop`, `OnTick`), the parser and typechecker for the new hook, and `src/codegen/library_runtime.rs.txt` (`OrchCommand`, the `Scripts` methods).
- **Do:** add `on_fixed_tick(step: float) { }` and `Scripts::fixed_tick(step)`, running in declaration order like `on_tick`.
- **Status:** Not in docs.
- **Done when:** a library test calls `fixed_tick` and `tick` in an interleaved order, and each hook runs only for its own call.
- **✅ Verified:** `engine_typed_tick_and_fixed_step` interleaves `fixed_tick_blocking` and `tick_blocking`; the fixed hook prints exactly once per `fixed_tick`, and `tick` returns only its own output. Documented in `docs/library-mode.md`, "Host lifecycle".

### ✅ 9. Route diagnostics to the host instead of stdout and stderr
- **Why:** the engine logs through `tracing`, and the editor shows logs in its console. Generated code prints straight to stderr and stdout, which a packaged game or the editor won't show.
- **Where:** `print` expands via `src/codegen/core.rs:5`. Warnings and errors use `eprintln!` at `src/codegen/expr.rs:183` (host call failed), `:230`, `:283`, `src/codegen/landline.rs:62`, `:71`, and `src/codegen/stmt.rs:215`, `:341`, `:490`, `:498`, `:591`, `:597`.
- **Do:** in library mode, send `print` output and runtime diagnostics through a generated `Host` method (e.g. `fn log(&self, level, message)` with a default implementation), or through the `log` or `tracing` facade.
- **Status:** Not in docs.
- **Done when:** a library test's `Host` receives `print` output and a failed host call's error message, and nothing is written to stdout or stderr.
- **✅ Verified:** `engine_host_logs_and_fast_shutdown` overrides `Host::log(LogLevel, &str)` and receives both the `print` output and the failed host call's error, while the host process's stdout stays empty. In library mode, `println!`/`eprintln!` in generated code route to `Host::log`, and Python and secret-child stderr is forwarded to it line by line. The test asserts on stdout only; Rust's process-wide panic hook still writes to stderr. Documented in `docs/library-mode.md`, "Logging".

### ✅ 10. Fast shutdown for editor Stop
- **Why:** the editor starts and shuts down a library instance on every Play and Stop. `shutdown` can wait up to three seconds for sidecar tasks (`docs/library-mode.md`, under "Host lifecycle"), which would freeze the editor's single thread.
- **Where:** `src/codegen/library_runtime.rs.txt` `OrchContext::cleanup` (the three-second `timeout`) and `Scripts::shutdown`.
- **Do:** add a configurable shutdown grace period (including zero), or a non-blocking shutdown that finishes cleanup in the background.
- **Status:** Not in docs.
- **Done when:** a test with a busy Python landline shuts down within a configured 100 ms.
- **✅ Verified:** `engine_host_logs_and_fast_shutdown` starts with `StartOptions { shutdown_grace: Duration::ZERO, .. }` and shuts down in under 100 ms while its Python landline is still busy. Documented in `docs/library-mode.md`, "Start options".

## Current implementation notes

- **Latest Rust:** generated libraries require stable Rust 1.98.1 and edition 2024.
- **Synchronous driving:** `ready_blocking`, `tick_blocking`, `fixed_tick_blocking`, and `shutdown_blocking` accept the host's runtime. A current-thread runtime runs no background work between pumps.
- **Host events:** typed `Scripts::trigger_<name>(...)` methods queue events synchronously, including before startup. Events drain in FIFO/registration order before and after each tick. Queues do not silently drop events.
- **Typed batches:** `on_tick(dt: float, input: Input) -> Output` generates `tick(dt, input) -> Result<Output, String>`. A typed hook must be the sole `on_tick`. Python handlers named `tick` use TICK (kind 9), with tick number, dt, handler ID, and batched arguments. Python exposes `self.tick_number` and `self.tick_dt`.
- **Deterministic subset:** `StartOptions { deterministic: true, ..Default::default() }` runs lifecycle/event hooks with host-accumulated dt. Event-handler `sleep` suspends until enough later tick time has passed; no wall clock is consulted. Ready events run FIFO, sleeping events remain queued. Spawned workers, serverlets/landlines, and sleep outside event handlers are explicitly excluded and rejected. Host implementations must themselves be deterministic.
- **Logging and Stop:** override `Host::log(LogLevel, &str)` to route logs to the engine. `StartOptions::shutdown_grace` accepts zero; awaiting shutdown still runs `on_stop`, which must cooperate. Rust's process-wide panic hook is outside this logger.
- **Python shipping decision (task 13):** the engine/player must ship a compatible Python runtime and dependencies, and set `StartOptions::python` to its executable path relative to the installed player. Development can use `ORCH_PYTHON`/`python3`. OrchestrateLang embeds the source/SDK, not the Python interpreter. No automatic runtime download and no embedded interpreter in this milestone. This decision is recorded here instead of editing the other docs, per the user's instruction.
- **Cross-target children:** `build --lib --target <triple>` passes the target to Cargo for both child binaries and library checking. The matching target/linker must be installed. Tests exercise an explicit native triple; foreign targets still need their platform toolchains.
- **Benchmark verified:** the existing harness ran 2,000 samples for each of 9 transport/payload combinations with p50/p90/p99/max output. Results are machine/load dependent; no timing claims are inferred from this one run.
- **Docs and plan:** `docs/library-mode.md`, `CHANGELOG.md`, `docs/language-reference.md`, and the VS Code grammar describe the new API. The Not-in-docs tasks are listed under "Host integration for the first adopter" in `docs/design/landline-serverlets.md` §8.
- **Verification (2026-09-15):** the full suite passes (53 unit, 10 snapshot, 1 error-case, 5 landline, 12 library, 18 runtime tests).

### 17. More languages (FFI first)

- **✅ Released in OrchestrateLang v0.4.0 (2026-09-15):** Zig, Swift, and TypeScript support below.
- **✅ Zig and Swift FFI (2026-09-15):** `load_foreign "zig"` (`export fn`, built with `zig build-obj` plus the platform archiver) and `load_foreign "swift"` (`@_cdecl`, or `@c` on Swift 6.3+, with the Swift runtime linked), using `.orch_ffi` sidecars with `int`/`float`/`bool`/`void`. Host target only. Examples: `examples/foreign_zig_math.orch`, `examples/foreign_swift_math.orch`.
- **✅ TypeScript 7 FFI bridge and landline serverlets (2026-09-15):** implemented and verified with TypeScript **7.0.2**, Bun **1.4.2**, and scriptc **0.1.1**. C# remains separate work.
- **✅ Automatic backend selection:** TypeScript 7 checks the implementation against its generated interface first. The complete wire-protocol adapter tries scriptc and falls back to `bun build --compile`. Type errors never trigger an unchecked fallback. Builds report the selection and retain `backend.txt` plus native fallback diagnostics alongside the artifact. `ORCH_TS_BACKEND=auto|scriptc|bun` can force a choice; forced scriptc failures are errors.
- **✅ FFI syntax:** `load_foreign "typescript" "math.ts"` in a module, with the normal `math.orch_ffi` sidecar and named TypeScript exports. `int` maps to `bigint`, `float` to `number`, `bool` to `boolean`, and `string` to `string`; arrays are supported by the Bun bridge. Example: `examples/foreign_typescript_math.orch`.
- **✅ Landline syntax:** `serverlet Counter via typescript(source: "counter.ts") { on add(amount: int) -> int }`. The source default-exports a class. An optional constructor receives `{ tickNumber, tickDt, host }`. Methods can be synchronous or return promises. Example: `examples/typescript_landline.orch`.
- **✅ Runtime integration:** protocol-v1 values, arrays/structs, TICK metadata, granted host callbacks, handler errors, per-call budgets, latest late results, host logging, and isolated instances reuse the existing landline interface. The asynchronous idle reader lets the Bun event loop continue between calls.
- **✅ Packaging:** generated libraries embed compiled TypeScript executables and extract them with executable permissions. Standalone builds copy them beside the program. Bun and TypeScript source are not required on the player's machine. Application data files and external native dependencies still need packaging. Cross-target TypeScript artifacts are currently rejected rather than embedding a host binary for the wrong target.
- **Tool setup uses Bun:** `bun add --dev typescript scriptc @types/bun`. The compiler searches source ancestors for `node_modules/.bin` before PATH; `ORCH_TSC`, `ORCH_SCRIPTC`, and `ORCH_BUN` override paths. Project `tsconfig.json` and installed Node/Bun types are used when present. No package installation happens automatically during a build.
- **Current boundary:** TypeScript FFI is a synchronous process bridge, not an in-process C-ABI library. One protocol process per imported module is reused across calls, preserving module state and avoiding repeated startup and handshake costs. Use a landline for independently started instances, host callbacks, ticks, or calls that need budgets. Landlines remain outside deterministic mode.
- **✅ Verification:** four new TypeScript integration tests cover native selection, Bun fallback, signature errors, large integers, strings/arrays, async replies, Bun APIs, typed ticks, host grants/logging, instance isolation, budgets/late results, and startup after source removal. The regression suite passed, with the four sandbox-blocked Zig/Swift checks passing on toolchain-access reruns.
- **Why:** the engine wants C# and TypeScript for gameplay and tools, and C++ plugins (`docs/design/landline-serverlets.md` §1).
- **Status:** Zig, Swift, and TypeScript are **done** (build step 12, v0.4.0). The rest is **Planned**, FFI first (`docs/design/landline-serverlets.md` §8):
  - Richer C-ABI types and opaque handles: step 10. C# via .NET Native AOT: step 11. Stateful FFI serverlets only if handles fall short: step 13.
  - Embedded Python via pyo3: step 14.
  - Process granularity is an open question (`docs/design/landline-serverlets.md` §10).
